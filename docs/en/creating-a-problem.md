# Creating a problem

*Español: [../es/crear-problema.md](../es/crear-problema.md).*

A problem can be prepared entirely in the administration, without the
command line. It needs the **all** permission or the **problem preparer**
one (`permission_tasks`); removing a task and adding it to a contest need
**all**. Every change goes to the [audit log](administration.md).

## 1. Create or import

- **Tasks → Add** creates an empty task with a `Default` dataset (Batch,
  100 points shared among the testcases), as CMS does.
- **Import a task package (zip)** uploads a zip of the
  [own format](package-format.md) (`problem.yaml`) or of CMS's formats
  (italy_yaml, Polygon, TPS). Before anything is written the page shows the
  **preview**: the errors and warnings of the validation and the list of
  changes (what would be created or updated, as `cms ctl import-task
  --dry-run`). **Confirm** writes it in one transaction. Zips are read
  with checks for zip slip, links and size.
- On the task page, **Update from a package** does the same over an
  existing task (the package's name does not matter: that task is updated;
  submissions are kept).
- If the package has `solutions/` (`correct.ac.cpp`, `slow.tle.py`…), the
  confirmation can submit them as **test submissions**.

## 2. Options and problem.yaml

The task page is the original CMS one (name, title, statements,
attachments, submission format, languages, tokens, limits, feedback,
score mode and, per dataset, limits, task and score types with their
parameters, managers and testcases).

The same options are shown as **problem.yaml**: download it, edit it on the
page or upload a file. **Preview** shows the changes; **Confirm** applies
them (the task is exported as a package with that `problem.yaml` and
imported back over it). **Download as a package** gives the whole zip.

## 3. Files one by one

**Add files** takes several files at once and recognises them by name;
the page lists what each one was taken for:

| Name | Stored as |
|---|---|
| `statement.pdf`, `statement.md`, `statement-es.pdf`, `statement/en.pdf` | statement (language of the name, or the one given) |
| `attachments/<file>` | attachment |
| `01.in`, `input.01`, `input_01.txt`, `tests/01.in` | input of testcase `01` |
| `01.out`, `01.ans`, `output.01`, `output_01.txt` | output of testcase `01` |
| `checker`, `manager`, `controller` | manager as it is (executable) |
| `checker.cpp`, `controller.cpp`, `manager.cpp` (Communication) | compiled with g++ as at import |
| `grader.cpp`, `grader.py`, `stub.c`, `*.h` | manager |
| `<name>.<verdict>.<ext>`, `solutions/…` | test submission |

A file named like an existing one replaces it. Testcases and managers go
to the dataset chosen.

## 4. Testcases one by one

Every testcase has its page (the testcase name in the dataset table): it
shows the beginning of the input and the output and lets you change them.
The input is **uploaded** or **written**; the output is **written**,
**uploaded**, left **empty** or **generated by the reference solution**.
**Write or generate a testcase** creates a new one.

**Generate inputs** runs a **generator** in the sandbox: upload its source
and write lines `name arguments`; the generator gets the arguments on its
input and what it writes becomes the testcase's input. With a reference
solution chosen, the outputs are generated next.

Generation runs are user tests of a hidden participant (see below) judged
by the dispatcher and the workers; the page lists the ones still running
and stores the results when reloaded.

## 5. Test submissions

**Test submissions** takes solutions with the expected verdict in the name
(`ac`, `pa`, `wa`, `tle`, `mle`, `re`, `ce`: `correct.ac.cpp`) or chosen
on the page. They are judged like any submission and the table shows the
outcome of each testcase and whether it matches the expectation:

- `ac`: full score; `pa`: some points;
- `wa`, `tle`, `mle`, `re`: some testcase with that outcome and not the
  full score; `ce`: compilation error.

Test submissions and generation runs use a **hidden, unrestricted**
participation of the reserved user `_preparer` in the task's contest
(created automatically) and are **not official**: they never count for
scores nor show on the scoreboard. So the task must be in a contest, and
they are judged on the live dataset and on those with **background
judging**.

## 6. What is missing

**What is missing** checks the chosen dataset: statement, testcases,
expected outputs (empty ones are flagged), valid score parameters
(subtasks and points), the managers and checker the task type needs (the
same validation as `cms ctl validate-task`), whether the dataset is
judged, whether a test submission expected to be `ac` is, and whether
every test submission gets its expected verdict.

## 7. Activating a dataset

To change the testcases of a task in a running contest, **clone** the
dataset, prepare it (with background judging) and use **Make Live**,
which shows which scores change and lets you notify the contestants, as in
CMS.
